# 0001 · 沿用壁画工作台，按比赛阶段交付

状态：规划采用。首个版本的工作量集中于线上单页卡和真实操作，现场路径在取得赛事权益后验证。

## 输入到输出

线上按“原图及来源 → 模型初稿 → 区域与依据 → 人工决定 → 观察卡与录屏”传递同一份案例。现场按“官方材料 → 千问办公任务 → 允许的百炼能力 → 人工选定候选 → 成果图、对比图、单页说明”处理。总决赛的输入是题目给出的决策条件，用一页框架整理证据和选择。各阶段单独建档。

| 模块 | 选择 | 原因与交接 |
|---|---|---|
| 图像界面 | 现有 HTML/CSS/JavaScript、Canvas，保留局部缩放与区域编号 | 线上工期短，现有页已经从选区通到 PDF。区域编号连接证据卡和复核动作，北齐的多边形编辑可在需要精细标注时引入 |
| 业务与导出 | Python 3.12 + Flask、ReportLab；沿用观察、导出、工作文件入口 | 报告预览、正式 PDF 与录像末帧使用同一已复核版本。输入过长给可操作提示，确保第一页文字清楚 |
| 图像处理 | Pillow、OpenCV、NumPy | 归一图像方向、映射坐标、取局部样本、生成同尺度对比、比较掩膜外像素。区域框用于说明位置；修复掩膜必须绑定原件像素尺寸 |
| AI | 线上通过工作台已有服务适配层；现场在千问办公中使用赛方列明的百炼能力 | 输出初稿含区域、可见特征、疑点、建议与风险，检查编号和字段后交队员。现场不调用 DeepSeek、本地 LaMa、骨鉴模型或第三方检测服务 |
| 持久化 | 首次送审保留现有 JSON 工作文件。需要自动存档时选 SQLite + 本地文件，部署沿用现有 Linux/WSL | 单机体验没有独立数据库服务依赖。将来出现多人同时审稿或多机器共享，再评估 PostgreSQL。先保留原 JSON 的恢复能力 |
| 知识与版本 | 赛事背景、原图局部、获授权参考各有编号，人工精读；同一区域可保存多条独立依据 | 少量材料可直接核对。不同出处互相冲突时同时保留原文位置。候选记录其父版本、理由、复核状态；否决仍可回查 |

## 数据关系与版本策略

一份档案关联一张原图及多条来源；一个区域关联若干来源和一个或多个复核版本。原图保存指纹、尺寸、方向和授权范围。来源保存名称、定位方式和使用条件。区域保存原图相对坐标、可见现象和解释。一条修订保存原文、改后文字、操作者、原因、时间。候选引用原图、掩膜版本、处理说明、结果文件和生成或导入记录。导出引用固定的复核版本及文件指纹，另保留真实平台操作记录的定位信息。

自动存档阶段先写完成的图像文件，再以事务登记引用；保存失败保留可读的上一版本。旧工作文件缺少来源或复核信息时显示待补，导出前由队员确认。模板内空值表示待填写，区域编号只在本档案内标识对象。

## 迁移清单

| 内容 | 动作 | 通过条件 |
|---|---|---|
| 工作台观察、人工校正、单页报告、校验测试 | 进入实现阶段后，逐模块核对权属、依赖和公开范围，再移植可公开部分 | 同一授权练习图完成真实操作与导出；公开历史里没有密钥、工作档案及受限图片 |
| 骨鉴 | 将证据卡、著录的设计转成新的壁画数据结构和交互 | 同一 R 编号能查到同一原图局部、来源及修订，正式卡片可读 |
| 北齐壁画 | 采用标注与审核思路，确需具体代码时单列来源、原版权与 MIT 声明 | 区域和候选有独立版本，默认演示生成器不进入修复路径 |
| 规则和示例 | 公开索引、原创归纳、空白字段。正式图像、录屏和平台记录按材料授权单独保管 | 仓库可公开阅读，提交包按规则另行制作 |

赛题与视频都允许披露后使用不含模型能力的通用库。携带自编辅助程序的范围须以赛时通知为准；整套本地工作台不作为现场默认操作平台。既有现场开关是防误用措施，无法证明实际在千问办公完成了任务。
